# Money Path Review

Real money moves through this code. Review the diff (`git diff origin/main...HEAD`) against every
item below. Report each item as ✅, ❌ (with file:line and a concrete failure scenario) or n/a. Fix
every ❌ before the PR merges.

## Amounts
- [ ] All amounts are integer minor units + currency. No floats, no `* 100` outside `common/money/`.
- [ ] Arithmetic goes through `common/money/`. Mixed-currency operations throw.
- [ ] Provider unit conversion is correct: **Flutterwave takes major units**; Stripe and Paystack
      take minor units. A test covers it.
- [ ] Totals come from the server-side quote function. Nothing trusts a client-sent price.

## Settlement
- [ ] Only `PaymentsService.settle()` sets a payment to `succeeded` or an order to `paid`.
- [ ] `settle()` checks that the reference is known, the provider matches, and the **verified amount
      and currency exactly equal** the payment's. A mismatch flags reconciliation and does not pay.
- [ ] Status transitions are conditional atomic updates (the expected current status is in the
      filter).
- [ ] Multi-document effects (payment, order, stock, coupon, entitlements, outbox, audit) happen in
      one transaction.
- [ ] Success is never downgraded by a late failure event.
- [ ] A late success on an `expired` order is honoured (re-reserve stock, or raise attention).

## Webhooks
- [ ] The signature is verified against `req.rawBody` with `timingSafeEqual` (Stripe via
      `constructEvent`).
- [ ] The Flutterwave event is re-verified through the API before settling.
- [ ] Deduped through the `webhook_events` unique index.
- [ ] Always 2xx after signature verification. Errors are recorded, never thrown as 5xx.
- [ ] `@Public()` + `@SkipThrottle()`. Signature headers are redacted from logs.
- [ ] Tests: valid signature accepted, invalid or missing signature rejected, duplicate delivery has
      no second effect.

## Idempotency and concurrency
- [ ] Order placement uses the `checkoutKey` idempotency key. A retry returns the same order.
- [ ] Payment references are generated by us and unique.
- [ ] Stock reservation is a conditional `$inc` (available ≥ qty in the filter).
- [ ] The partial unique index "one successful payment per order" is intact.
- [ ] Concurrency tests exist for the path (parallel settle, parallel last-copy checkout).

## Refunds
- [ ] Two-phase: claim the refundable balance atomically, then call the provider with an idempotency
      key.
- [ ] A confirmed rejection reverts the claim. A timeout or 5xx becomes `outcome_unknown` +
      reconciliation, and is **never auto-retried**.
- [ ] Over-refund is impossible (the balance check is in the atomic filter).
- [ ] A full refund revokes entitlements. Audit entry written.

## Access and emails
- [ ] Library, download and read endpoints check the entitlement (not revoked) and ownership.
- [ ] The preview never exposes the manuscript URL or locked pages.
- [ ] Receipt and other money emails go through the outbox with a `dedupeKey`, inside the settlement
      transaction.

## Operational
- [ ] Logs include `orderId`, `reference` and `provider`, and exclude secrets and full provider
      payloads.
- [ ] Anything ambiguous surfaces in the admin "Needs attention" queue.
- [ ] Env vars for new secrets are in Joi validation, `.env.example` and the DEPLOYMENT.md §4 production table. Live keys
      are production-only.
